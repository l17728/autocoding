# PM 工作对话：需求、UX 与实现规格

## 目标与范围

首页的 PM 工作对话是 Owner 与 PM 的项目级入口。Owner 可查询进展、讨论方案、暂停或继续派发、补充需求。PM 应报告当前事实和下一步；只有在需要业务取舍、缺失权限或外部依赖不可用时才求助。所有对话与项目状态按项目隔离并持久化；全局输入历史仍由平台历史服务统一保存。

本版本实现持久化对话、进度查询、暂停/继续指令、明确实施语句委派、上下文讨论分析和状态变化汇报。对话分类使用确定性规则：先排除疑问与否定，讨论意图先于开发意图；只有明确命令进入委派。讨论交由 PM 模型结合当前项目事实、近期对话和已审核知识回答；失败时明确报告，不改计划或派发任务。复杂需求拆解仍走既有计划提案与 Owner 采用流程。

## UX

对话区位于项目概览与任务工作区之前，默认展开。顶部显示总体进度、已验证任务数、批次状态、活动任务及暂停原因。消息按时间排列，区分 Owner 与 PM，并显示消息类型与本地时间。输入框接受自然语言；发送过程显示处理中状态，失败时保留草稿并展示错误。

PM 对话只显示 Owner 输入、PM 汇报和安全摘要。默认载入最新 100 条，并按时间顺序显示；“加载更早的对话”使用偏移分页。历史搜索在 SQLite 执行过滤、计数和分页，支持消息正文、类型和关联 ID。Agent 的完整脱敏输入输出仍在 Agent 实时控制台查看。任务和批次引用可点击并滚动到工作区对应区域。后台服务从持久化事件账本读取游标，只在任务、批次、暂停和验收等相关事件发生时刷新项目状态并追加汇报；浏览器关闭时仍运行，不重复记录相同状态。草稿和待确认的发送编号按项目保存在浏览器 session storage；发送失败后重试沿用原消息 ID 与幂等键，输入框中后续编辑内容不会被旧请求清空。

## 状态与数据

消息键为 `pm_dialogue:{message_id}`，字段为 `project_id, actor, kind, content, references, state, created_at`。消息写入项目本地 SQLite metadata 表，并产生不含消息正文的审计事件。输入长度上限 12,000 字符；持久化前执行凭据脱敏。

接口：

- `GET /api/v1/projects/{project_id}/pm/dialogue?offset=0&limit=100&q=...` 返回最新优先的分页对话与当前项目状态；`q` 最多 200 字符，按消息正文、类型和引用 ID 检索；消息页按时间升序呈现，`has_older` 精确指示是否可继续翻页。
- `POST /api/v1/projects/{project_id}/pm/dialogue/messages` 接收 `message_id` 和 `text`，必须带 `Idempotency-Key`。同一幂等键与请求体重试不会重复委派。
- 对话输入自动分类为进度查询、暂停、继续、讨论、明确实施需求或普通记录。只有明确实施动词会调用现有委派工作流；普通确认语不会假称已执行。

处理顺序为 `received -> recorded -> classified -> acted/reported`。用户输入先写入账本；写入委派前经过现有外部操作幂等与对账保护。服务重启后可查询已有消息。对不确定是否投递的 Agent 指令，继续既有运行恢复流程，不由对话接口重新发送。

## PM 行为与安全边界

1. 查询：从项目 Dashboard 读取进度、任务、批次和活动运行，回复可核验事实。
2. 暂停/继续：更新项目派发状态；继续操作交由 Coordinator 从持久化检查点恢复。
3. 讨论：将 Owner 想法、当前项目快照和近期对话交给 PM 模型分析，说明影响、风险/未知项和建议下一步；不直接修改计划或派发任务。模型不可用时保存输入并明确说明分析失败。
4. 新需求：疑问、否定和明确讨论优先于动作词；“先讨论，不要开发”“能否修复”等不得委派。明确的“修复/实现/开发”等指令进入现有委派工作流；接受后生成任务/批次引用。PM 自动生成验证基线，Owner 提供业务验收意图，不需要配置命令或 JSON。
5. 普通输入：记录到对话并明确说明尚未触发开发任务，避免误导用户。
6. 隐私：凭据由 Redactor 脱敏；项目消息保存在各自项目数据库。Agent 原始会话内容不复制到此处。

## 验收与评审记录

- 查询回复与消息持久化：`tests/test_pm_dialogue.py`。
- 搜索全历史及分页、PM 讨论上下文、模型失败回退、状态变化主动汇报与关联引用：`tests/test_pm_dialogue.py`。
- 暂停审计与普通输入不冒称执行：`tests/test_pm_dialogue.py`。
- API 访问仍受 Owner 身份依赖和 `external_once` 幂等保护。
- 监督器使用 Windows 文件锁防止重复实例；工作进程异常退出时清理子进程；HTTP liveness 与业务探测分开，业务探测失败写日志而不因认证或项目 API 错误误重启服务。
- 监督器在服务首次就绪前允许最多 150 秒的项目/Agent 冷启动恢复；worker 已退出会立即重启。一旦健康端点首次成功，立即开始 liveness 和业务状态监控。健康端点使用 3 秒超时，连续三次 liveness 失败后重启工作进程；业务列表/快照使用 10 秒超时，业务 API 错误只记录诊断，只有明确的运行批次停滞才触发恢复。监督器验证端口项目根目录，启动脚本以互斥锁覆盖端口检查至进程登记。Windows 重启和退出时递归清理受控进程树，避免留下 Python 子进程占用端口。`reconciling` 状态允许等待证据或 Owner，不视为死锁。
- 2026-10-21 实机检查：OpenCode CLI 1.19.3 可启动，网络 DNS/TCP/TLS 可达；带自定义 glob 插件的首个 session 请求超时。平台默认关闭该兼容插件后，使用现有智谱配置成功建立 OpenCode session 并收到模型回复。该验证不证明长时间任务、工具调用及所有验收条件通过。

剩余验收限制：真实供应商连接、长时间业务负载、Windows GUI 手工可用性及故障注入后的完整服务恢复需要在运行环境验收；仅靠单元测试或本机健康端点不能代替这些验收。
