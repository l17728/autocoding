# PM 工作对话：需求、UX 与 SDD（草案）

## 目标

首页的 PM 工作对话是 Owner 与 PM 的主入口。Owner 可以查询、讨论、下达进一步指示和补充需求；PM 主动汇报推进、风险、验收与求助。PM 先在授权范围内诊断、恢复或调整计划，只有需要外部信息、权限、账号、业务取舍或网络恢复时才求助。

## UX

对话区固定在项目概览下方，默认展开。顶部显示“PM 当前判断”：总体进度、批次状态、活动任务、最近风险和下一步。消息按时间排列，并带 `汇报`、`指示`、`需求`、`求助`、`恢复`、`验收` 标签；每条任务/批次引用可点击定位到任务清单、控制台或证据。

输入框支持自然语言。发送后即时显示 Owner 消息和“PM 正在分析”；PM 回复包含结论、已采取动作、证据链接、是否仍需 Owner 回复。需要决策时使用结构化选项，但始终允许自由文本。历史可按项目、任务、批次、标签检索；全部 Owner 输入进入全局去重历史。

摘要与原文边界：PM 对话显示 PM 结论、Owner 输入和安全的执行摘要；真实脱敏 Agent 指令与输出只在任务实时控制台显示。

## 状态机

`received -> diagnosing -> acting -> reported -> resolved`。无法自主处理时进入 `awaiting_owner`，必须带原因、已尝试动作、影响、可选项和继续条件。每一步写入审计事件与对话记录；服务重启后从最后持久化状态恢复，绝不重复不确定的 Agent 输入。

## 数据与接口

`pm_dialogue:{id}` 保存不可变消息：`project_id, actor(owner|pm), kind, content, references, state, created_at`。`POST /pm/dialogue/messages` 接收 Owner 输入并幂等落盘；PM 分类为查询、指示、需求、讨论或故障报告。`GET /pm/dialogue` 返回分页消息和当前 PM 判断。后台执行只通过已有计划、批次和恢复 API，不由页面直接重复发 Agent 指令。

## PM 行为

1. 查询：读取快照、运行、批次、健康和证据，给出事实与不确定性。
2. 指示：关联现有任务；可自动执行的则更新计划并推进。
3. 新需求：形成提案、影响分析和验收草案；采用后进入 DAG。
4. 故障：收集证据，执行安全恢复或 Provider 切换；无法恢复才求助。
5. 汇报：任务状态变化、停工、恢复、验证和收尾均生成 PM 消息。

## 验收与 Review

- Owner 可连续发送查询、指示和新需求，重启后历史与上下文仍存在。
- 每个运行/恢复/验证状态变化产生可定位 PM 汇报。
- PM 不会因普通查询启动模型或重发任务。
- 对话内容、模型凭据和思考内容均不泄露；输出经过脱敏和大小限制。
- 评审维度：交互可理解性、调度正确性、断线恢复、幂等与审计、性能、隐私、可访问性。
