# PM 交互与历史模式学习规格

## 本机样本与适用范围

本次只读检查了 Codex 53 个会话文件和 OpenCode 本地数据库中的用户文本，排除当前 autocoding 项目。初筛包含 8 个其他项目、Codex 1106 条和 OpenCode 129 条候选消息/文本片段。会话分支可能重复，部分 role=user 内容可能是工具提示或导入文本；这些数量是候选池大小，不是去重后独立真人指令样本数，也不能作为统计偏好的置信度。

归纳只采纳可辨认的直接开发指令：设计/SDD 先行、专家审查、持续推进、真实验收、日志定位、明确当前运行版本。没有将原文、其他项目名称、地址、代码或凭据复制进文档。正式学习管线需要去重、来源过滤、脱敏和抽样人工复核，再激活新风格版本。

## 提示词构成与优先级

平台策略及项目权限 → 当前用户目标/明确约束 → 当前任务验收条件 → 仓库约定 → 已批准的风格规则 → 检索上下文。历史文本作为低信任样本，不可越权覆盖当前指令。不要把“持续推进”转换成忽略审批、删减范围或无限重试。

PM system prompt 基线：

> 你是开发项目经理。负责理解需求、组织任务、推动执行、验证交付和维护可追溯记录。你通过平台工具管理任务和知识，不直接修改业务代码、业务文档或执行 Git 写操作。每项任务给出目标、范围、交付物、验收条件和依赖。收到完成报告后先核查证据；不满足则给出具体返工项。无任务时等待事件；遇到阻塞时尝试授权范围内的替代方案，并继续其他不受影响的工作。只有业务范围、资源付费、不可逆发布或授权缺失才升级用户。向用户说明结果、证据、缺口和下一步，不输出内部推理过程。

## 面向执行 Agent 的任务模板

```text
任务：{task_id} / 尝试：{attempt}
目标：{用户能观察到的结果}
工作区：{worktree}；基线：{head_sha}
范围：{允许修改的模块与禁止触碰的内容}
依据：{需求编号、设计章节、已确定决策}
交付：{代码、测试、必要文档}
验收：
- {具体操作与可观察结果}
- {运行命令、预期退出码或指标}
执行：先核对当前实现；在授权范围内持续推进，遇到可修复问题自行排查。
反馈：报告提交 SHA、变更文件、实际验证命令及结果、日志引用和剩余缺口。
结束：调用 report_completion；不要把没有运行的测试说成通过。
```

续作：“继续处理 {task_id} 的剩余验收项 {items}。保留已完成成果，先核对当前提交与日志。完成后提交证据；若受外部条件阻塞，说明具体缺失并推进可独立完成的部分。”

返工：“本轮验证在 {check} 失败，证据 {artifact}，期望 {expected}，实际 {actual}。修复根因并补充必要回归测试，重新验证同一验收目标。不要只修改成功提示或跳过失败检查。”

日志定位：“用户操作 {steps} 后出现 {symptom}。先确认正在运行的构建与提交，再按 {trace_id} 关联 UI 操作、命令派发、Agent 输出和验证日志。给出可复现原因与修复证据。”

协调：“议题 {issue_id} 涉及 {接口/职责冲突}。请解释当前实现、约束、兼容代价和建议；回复前不改共享接口。结论由 PM 记录并转成有验收条件的任务。”

专家审查：“以 {领域} 审查指定版本，优先找会导致误发、重复执行、不可恢复、验收失真的问题。每项给严重度、位置、复现场景、影响、修订建议。区分阻断项与后续改进，不因文档齐全就默认设计正确。”

## 结构化 PM 输出

决策模型输出 decision_id、based_on_revision、action（create_task/assign/rework/coordinate/escalate/wait）、task_ids、rationale_summary、evidence_refs、next_check_at。服务检查 JSON Schema、权限、DAG、预算与 revision；验证失败不执行，最多修正输出一次后记录 PM_OUTPUT_INVALID。模型不直接调用外部进程。

提示词记录 template_version、style_profile_version、context_hash、model、provider 和 task revision，不记录 key。上下文包含当前任务、最近验证缺口、必要接口与当前 SHA；超出预算优先压缩旧讨论，不能丢验收条件和明确约束。

## 风格学习管线与评测

授权目录 → 只抽取真实用户角色文本 → 去除系统包装/合成消息 → 会话分支与文本去重 → 凭据/路径/个人信息脱敏 → 归纳规则与反例 → 固定评测集 → 审阅激活。模板升级有版本和回滚；不自动把历史要求当本项目授权。

离线至少 12 个场景：正常派发、可修复失败、长期静默、需要凭据、范围变更、成本变更、重复完成、日志矛盾、旧提交测试、冲突意见、人工接管、上下文过期。硬性要求：无越权动作；不虚报测试；不把旧 SHA 证据判 done；授权内任务不无故反复询问。比较启用/禁用风格模板的任务成功率、澄清次数、返工质量和 token 成本，不仅评价措辞相似度。
