# 创建失败、进程清理与交互矩阵专项

## 范围与实现

本轮按 Owner 要求推进四项：创建失败诊断与有界重试、Windows 进程树清理、真实 Agent 交互矩阵、完整回归。智谱真实供应商测试与已搁置的长期业务负载不在本次执行范围。

### 创建失败与重试

`TerminalStartError` 保存创建阶段、允许公开的异常类型、整数 Windows/系统错误码及清理确认结果，不保存异常原文、命令行、环境或凭据。阶段包括 Job、监听器、PTY、进程、输出桥、输入连接、鉴权与会话绑定。

仅在确认失败尝试的资源已清理后，才能执行下一次创建。创建失败和就绪失败共用一个尝试上限，默认三次；耗尽后等待明确再次启动。未知投递、已有用户输入、停止未确认均不自动重试。创建重试等待期间网页允许停止，禁止同时恢复。

旧 `CONPTY_START_FAILED` 未保存底层错误，不能追溯断言其唯一根因。本次解决诊断丢失和重试范围缺口，不承诺所有供应商或系统启动故障消失。

### Windows 关闭

父进程持有命名 Job，监督进程先加入 Job 再启动 CLI。关闭前保留已验证属于该 Job 的进程句柄，终止整组并等待这些句柄及 Job 活跃进程计数；随后关闭私有输入与输出桥、释放句柄和草稿目录。

Job 已开始终止时，额外 `TerminateProcess` 可能返回 Windows 5。这里只允许继续等待原句柄变为已退出，超时仍报告停止未确认。某个清理步骤失败时继续释放其余资源，保留首次错误，不允许未知进程被自动恢复替换。

新增真实父子进程三轮关闭测试：每轮等待子进程句柄已退出后立即重命名工作目录，不依赖删除重试。早期未等待子进程和 Windows 5 竞态的失败记录均保留。

### OpenCode 拒绝后的回合结束

真实 CLI 配合本地模拟供应商复现：拒绝工具后，CLI 空闲，工具状态为错误，消息已完成但 `finish=tool-calls`。旧适配器将所有此类消息当作中间步骤，导致 PM 一直等待。

现在只有本回合实际成功送达的拒绝、对应工具错误、所有工具已结束、无待答审批/提问、会话空闲和消息完成同时成立，才报告 `interrupted`。不会仅凭拒绝 HTTP 回执或不相关工具错误宣布结束。测试覆盖忙碌、待答请求、工具仍运行及不相关调用的反例。

## 交互验证方法

- `tools/local_interaction_probe.py`：真实 Claude/OpenCode CLI，隔离配置和本地脚本化 HTTP 供应商。检查多选、自定义回答、实际批准文件、拒绝无文件、进程重启后上下文、取消结束以及后续新回合。使用虚构本地 key，不调用智谱。
- `tools/codex_interaction_probe.py`：实际 Codex 模型、隔离工作目录，检查原生问题和自定义答案、批准/拒绝副作用、上下文恢复、取消及后续回合。使用本机导出协议的实验性 Plan 模式触发原生问题，生产适配器默认模式不变。
- 原生浏览器用例与通用 UI 用例检查终端菜单、输入所有权接管、停止/恢复以及错误展示。协议问答测试不能替代各 CLI 每一种 TUI 对话框的人工可用性检查。

## 边界

本地脚本化供应商验证 CLI 的协议、工具和会话处理，不证明真实供应商模型质量、配额、断连恢复或智谱可用性。隔离样本不代表长期真实业务。原生启动验收遵循最多三次独立尝试、至少一次完整通过；修复前失败保留，修改代码后重新验收不与旧结果混为连续成功。
